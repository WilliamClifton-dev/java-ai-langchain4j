# HBTI Coach 简历素材

## 一句话定位

独立构建一个基于 Spring Boot、React 和 LangChain4j 的 AI 体重管理应用：确定性服务负责测评、计划、追踪和复盘，AI 负责解释、追问和受限工具调用。

## 当前可核验技术栈

- Java 17、Spring Boot 3.5.16、Maven
- LangChain4j 1.0.0-beta3、MiniMax / Ollama 兼容接口
- MySQL 8、MyBatis、Flyway、Redis
- React 19、TypeScript、Vite、React Query
- Docker Compose、GitHub Actions、k6 脚本

## 推荐简历版本

**HBTI Coach | AI 健康管理应用**

- 设计模块化单体，打通 HBTI 测评、版本化健康计划、每日追踪、每周复盘和 AI 教练完整用户流程。
- 建立确定性业务与 AI 的边界：模型只能调用服务端注册的类型化工具，用户归属、参数校验、幂等、事务和持久化由代码负责，降低提示词注入导致越权写入的风险。
- 实现 Cookie JWT、刷新令牌轮换、CSRF、资源归属、审计日志、SSE 流式超时/取消/熔断和 Redis 临时状态策略。
- 建立默认离线质量门禁，涵盖后端业务/迁移测试、前端交互测试与生产构建；使用 H2 和 Mock 模型，不依赖外部数据库或模型服务。当前测试数量见[项目状态报告](PROJECT_STATUS_2026_09_18.md)。
- 提供离线 AI/RAG 安全评估、Docker Compose 健康冒烟、k6 L1 负载、备份恢复和回滚脚本；实际发布指标以 `target/release-evidence/` 中的运行报告为准。

## 面试时可以展开的三个决策

### 1. 为什么不让模型直接写业务事实？

模型输出是不稳定的外部输入。计划、打卡、测评结果和周报必须经过确定性服务校验、用户归属检查、事务提交和幂等控制。模型可以提出建议或选择显式允许的工具，但只有工具成功返回后，系统才会声称事实已保存。

### 2. 为什么采用模块化单体？

当前功能需要跨领域事务和一致的用户归属检查，单体部署降低了运行成本；Java 接口边界保留了未来拆分的可能。当前仓库没有把“未来可拆分”表述成已经运行的微服务。

### 3. 如何证明质量？

默认测试验证业务规则、权限、迁移、流式协议和前端状态；离线评估验证提示词边界与检索上限；Compose、负载和恢复脚本验证交付路径。真实模型体验和生产平台能力需要单独运行并记录证据，不能用单元测试数量代替。

## 不要在简历中写成已验证成果的内容

- “支持 10,000+ 用户”或“10,000+ 并发”
- “p95 降低 60–80%”或固定的 p95 数字，除非附带环境、数据集、命令和报告
- “100% 测试覆盖”“安全 A+”“全面生产就绪”
- 未由当前项目状态报告或 commit 绑定运行报告支持的测试数量和性能数字

## 可补充的证据

执行 [RELEASE_EVIDENCE.md](RELEASE_EVIDENCE.md) 中的命令后，把带 commit SHA 的报告放入 `target/release-evidence/`，再把实际的 p50/p95/p99、错误率、首 token 延迟和资源规格写进简历。没有报告时，使用“提供脚本”“已建立门禁”这类准确表述。
