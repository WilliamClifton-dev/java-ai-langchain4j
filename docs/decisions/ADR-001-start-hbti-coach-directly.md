# ADR-001: 跳过医疗版并直接进入 HBTI Coach

## 状态

Accepted；其中 MongoDB 存储决定已被 ADR-002 取代

## 日期

2026-08-14

## 背景

原计划先完整实现硅谷小智医疗版，再复用聊天记忆、Tool Calling、RAG 和流式输出能力改造为 HBTI 体重管理助手。实际开发过程中，医疗课程代码与提前创建的 HBTI 半成品同时存在，造成类名与文件名错位、重复配置、空类和 Prompt 路线冲突。

项目的主要目标已经明确为 HBTI 个性化体重管理平台。继续完成医疗业务会延迟目标产品，并产生随后还要删除的预约领域代码。

## 决策

停止医疗助手运行路线，当前 Java 仓库直接作为 HBTI Coach 后端：

- 删除医疗课程 Demo Assistant 和重复测试；
- 保留已经可复用的模型切换、MongoDB ChatMemory 和 LangChain4j 基础；
- 先建立 `API -> 场景 Prompt -> Agent -> ChatMemory` 纵向切片；
- HBTI 评分、计划、记录、周报、RAG 和流式输出按独立纵向功能逐步实现；
- 不通过空 Controller、空 Tool 或无法运行的 DTO 提前占位。

## 备选方案

### 继续完成医疗版

- 优点：沿用课程顺序，参考资料完整。
- 缺点：业务代码最终不会进入目标产品，继续扩大双路线混乱。
- 结论：拒绝。

### 同时保留医疗版与 HBTI 两套 Agent

- 优点：可以演示更多场景。
- 缺点：共享模型、记忆和 Prompt 配置的边界不清，测试与维护成本翻倍。
- 结论：拒绝。

## 后果

- 当前仓库只保留 HBTI 业务方向，结构更容易理解和测试；
- 原演进架构文档中的医疗阶段只作为历史方案参考；
- 将失去一个完整医疗预约课程成品，但避免把课程 CRUD 当成目标产品业务；
- 后续每项 HBTI 能力必须真正实现并通过测试后再进入主代码。
