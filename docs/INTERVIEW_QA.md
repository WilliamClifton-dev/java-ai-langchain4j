# HBTI Coach 面试问答

本文只使用当前仓库可以核验的事实。性能、真实模型质量和生产部署结论必须带对应报告，不用估算值替代。

## 1. 请介绍这个项目

HBTI Coach 是一个 AI 体重管理应用。用户可以完成行为倾向测评，生成版本化计划，记录每日体重、饮食和训练，并生成每周回顾；AI 教练负责解释和追问，也可以在服务器授权下读取或写入有限的业务数据。

核心设计是把 AI 放在“解释与建议”边界内。HBTI 评分、BMI/BMR/TDEE、计划状态机、用户归属、幂等和持久化全部由确定性代码负责，因此模型故障不会让核心记录功能失效。

## 2. 为什么选择模块化单体

项目当前需要跨领域的一致性和较低部署成本。`identity`、`profile`、`assessment`、`planning`、`tracking`、`coach` 和 `knowledge` 通过 Java 接口协作，不依赖内部 HTTP。这样保留单体的事务边界，同时让领域依赖显式。未来是否拆分，要以真实流量、团队边界和运维成本为依据，而不是把“可拆分”当作已完成的微服务。

## 3. 如何防止提示词注入造成越权

提示词不是权限边界。工具执行上下文从 JWT subject 和服务器注册表派生，用户或模型提供的 owner 参数不参与授权。写工具还使用幂等键，避免重试重复写入；流式请求取消或完成时会释放许可并清理上下文。权限、校验和事务都在应用服务层执行。

## 4. 为什么健康计算不能交给模型

模型输出可能变化，也无法提供可审计的计算保证。HBTI 评分、BMI/BMR/TDEE、目标范围和计划生命周期采用版本化确定性规则，并用黄金固件和集成测试验证。AI 只能解释结果、提出反思问题或生成待确认建议。

## 5. 你如何做性能优化

周回顾按 `user_id + local_date` 查询多个七日窗口，因此迁移中加入复合索引并用测试验证迁移可执行。当前仓库提供 k6 L1 负载脚本和固定阈值，但某次具体运行的 p95、p99 和错误率只有在生成 `target/release-evidence/load/report.json` 后才能作为简历数字。没有报告时，我会说“建立了可复现负载门禁”，不会声称已经支持某个用户规模。

## 6. 测试如何运行

默认测试使用 H2、Mock 模型和测试配置，不需要外部数据库或模型 API。当前数量和最近验证时间见[项目状态报告](PROJECT_STATUS_2026_09_18.md)。真实模型测试由 `RUN_EXTERNAL_TESTS=true` 显式开启，不能和默认离线质量门禁混为一谈。

## 7. 项目现在是否生产就绪

准确说法是：核心功能和 L1 离线证据已具备，仓库提供 Compose、负载、恢复和回滚脚本；公开生产还需要 TLS、托管密钥、异地加密备份、告警、镜像 digest 和实际运行报告。项目没有把测试环境通过等同于全面生产认证。

## 8. 下一步改进

先统一版本和证据口径，再在固定环境执行 Compose、k6、恢复和真实模型评估；把报告绑定到 commit SHA。产品侧继续完善首页下一步引导、测评草稿恢复和真实模型体验评审。只有数据证明收益后，再考虑 Spring Boot 升级、向量检索或 AOT 等扩展。
